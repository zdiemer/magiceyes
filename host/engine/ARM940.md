# ARM940T second-core emulation (GP2X dual-core)

The GP2X has two CPUs sharing one 64MB SDRAM: the **ARM920T** (main, runs Linux + the game) and
the **ARM940T** (auxiliary, ARMv4T, MPU not MMU). Homebrew offloads work to the 940 — notably
**gpu940**, the soft-3D renderer used by **egoboo2x** (and the Code Alone demo). Supporting those
titles means actually running the 940.

## Control protocol (MMSP2 register block @ phys 0xC0000000)

Verified against `load940`'s disassembly (egoboo's `gpu940` package) and devkitPro **orcus**
`source/940.c`:

| Reg (offset) | Name | Meaning |
|---|---|---|
| `0x0904` | SYSCLKENREG | bit0 = ARM940 clock enable |
| `0x3b48` | DUALCTRL940 | bit7 = halt(1)/run(0); **bits0-6 = memory bank** |
| `0x3b40` | DUALINT920 | 920←940 interrupt (cleared at init) |
| `0x3b42` | DUALINT940 | 940←920 interrupt (cleared at init) |

**Memory bank:** the 940's address space is a flat offset into physical RAM:
`940_addr A → phys (bank * 0x1000000 + A)`. gpu940 uses **bank 2** → the 940 sees phys
`0x02000000` at its address 0. That's exactly where `load940` loads the firmware and the base of
our shared `g_pram` pool — so the 940 uc maps `g_pram` at address 0.

**Start sequence** (load940): assert halt + set bank (`0x3b48 = (old&0xff00)|0x82` → halt, bank2),
clear `0x904` bit0, load firmware to phys `0x02000000`, then release: `0x3b40=0; 0x3b42=0;
0x904 |= 1` (clock on); `0x3b48 &= 0xff7f` (clear bit7 → **run**). The 940 begins at its reset
vector (addr 0).

## gpu940 firmware (`gpu940`, raw ARM940 blob, ~36KB)

Bare-metal ARM940T linked at address 0:
- `0x00`: exception vectors (`b 0x20` reset; the rest `ldr pc,[pc,#...]`).
- `0x20`: reset — CP15 MPU setup (`mcr p15, cr6` regions, `cr2/cr3/cr5` cache/wb/perms,
  `cr1 = 0xc000107d` enables MPU+caches), `sp = 0x80000`, `bl 0x6b8` (main), loop.
- It's a **separate-process software renderer**: the client (egoboo) sends commands via a **cyclic
  buffer in shared memory**; gpu940 rasterizes into video buffers (also in shared RAM). gpu940 has
  a PC build doing the same over an mmap'd buffer.

## Emulation plan

- **[940-1] DONE** — shared physical RAM (`g_pram`, phys `0x02000000-0x04000000`); every `/dev/mem`
  mmap is a window so 920 + 940 alias the same bytes (`mem.c`).
- **[940-2] DONE** — `me940.c`: a second `uc` (`UC_CPU_ARM_946`, MPU-equipped) with `g_pram` mapped
  at addr 0 and the MMSP2 block at **`0xBE000000`** (the 940's own view — the firmware reads this
  base from its global `@0x6a90` and indexes the MLC regs off it; NOT the 920's `0xC0000000`).
  Started/stopped by trapping `0x3b48`/`0x904` in `mmsp2_write_cb`; start is gated on a halt→run
  transition **and** a plausible ARM reset vector at `g_pram[0]` (first word `0xea……`), so unrelated
  `0x3b48` writes (Payback/vektar poke it) don't spuriously start a core. Runs on a host thread; a
  940 fault logs + halts the 940 only. **Verified** (`ME_940_SELFTEST`): the real gpu940 firmware
  runs its reset/CP15-MPU init and its main command-loop cleanly (40M+ insns, no fault) — it just
  spins waiting for client commands.
- **[940-3] DONE** — instead of the (unreliable) program-reload path, the engine emulates the
  trivial `load940` inline: the loader records the `load940 <fw>` firmware (`scan_940_firmware`) and
  `main` brings the core up (`me940_load_and_start`) before the client game. The real gpu940 firmware
  then runs live alongside egoboo, sharing the upper-RAM command buffer (1.6B+ insns, rasterizer
  active across 25/64 code-KB buckets — it IS processing egoboo's commands).
- **[940-4] PARTIAL** — egoboo renders: gpu940 rasterizes its frames into a shared video buffer and
  the engine presents it (`me940_scan_fb` follows the rendered buffer; egoboo `black 1.00 → 0.38`,
  real content). gpu940 programs the MLC via `0x2880`/`0x2916-0x291c` (not the 920's OADR/EADR) and
  its declared scanout reg doesn't point at the live buffer, so present currently locates the output
  by content. **Open:** the result is striped — the content-scan can land on a render-target/texture
  rather than the display buffer, and the exact video-buffer stride/format isn't pinned. Needs
  gpu940's console-struct layout (its source) to read the true display-buffer pointer + pitch.
  DUALINT920/940 cross-core IPC also not yet modelled (the gpu940 protocol polls shared memory, so
  egoboo runs without it).

Unicorn has `UC_CPU_ARM_946` and `uc_ctl_set_cpu_model`, so the firmware's CP15 MPU runs natively.
